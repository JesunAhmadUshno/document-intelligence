## Learn stage (moved from level-1-learn/README.md)

Status: DONE (2026-11-05). Rule-based field extraction from
synthetic plain-text invoice and form documents, with a per-field
confidence score, an eval harness against labelled ground truth,
and a review queue, built with the Python standard library only.

### Honest scope line

There is NO OCR and NO real documents and NO LLM in this level.
Every document is a synthetic plain-text fixture authored in
documents.py, with invented vendor names. The input is already
text, so nothing is scanned, photographed, or read from an image.
OCR plus LLM extraction is Build level scope.

### Method

1. Fixtures. Eight synthetic documents (seven invoices, one form),
   each with hand-labelled ground truth for five fields:
   invoice_number, date, vendor, total, and due_date. One field is
   genuinely absent (D04 due_date, ground truth None). D08 carries
   a date in an unsupported format and a total written in words:
   its ground truth holds the true values, and the extractor is
   expected to miss both.
2. Extractors. One regular expression extractor per field. Each
   tries, in order, a primary labelled pattern, alternate labelled
   patterns, and (for date and vendor) an unlabelled fallback.
   Money values are normalised by removing commas. Extracted
   values are strings, or None when nothing matched.
3. Confidence. A stated rule, the same for every field: 1.00 for a
   primary labelled match in the expected format, 0.80 for an
   alternate labelled match, 0.60 for an unlabelled fallback
   match, and 0.00 when nothing matched. The score describes the
   match route only. It is not a calibrated probability.
4. Eval harness. Each extraction is compared with ground truth
   for exact equality. A correctly detected absence counts as
   correct: D04 due_date is None in both the extraction and the
   ground truth. Accuracy is reported per field and overall.
5. Review queue. An extraction goes to the review queue when its
   confidence is below 0.80 or its value is None. The queue lists
   the document, the field, the confidence, the extracted value,
   and the reason (missing or low confidence), so a human checks
   exactly those fields first.

### Failure modes and limits

- Synthetic text only: eight small authored documents. Real
  invoices vary in layout, wording, and noise, and none of that
  variation is measured here.
- No OCR and no LLM: the input is already clean plain text. Image
  documents, scans, and PDFs are out of scope for this level, and
  no claim is made about extraction from them.
- Narrow formats: dates are supported in ISO form only, money
  only as a dollar amount with two decimals, and only the named
  label variants are recognised. D08 shows the cost: a written-out
  date and a total in words are both missed.
- Fallbacks can mislead: the vendor fallback takes the first
  plain line of the document, and the date fallback takes the
  first ISO date outside a due date line. Both are right on these
  fixtures at 0.60 confidence, and the review queue exists
  because that route is not trustworthy in general.
- Confidence is a route label, not a probability: a 1.00 match
  can still be wrong on a document whose label is used for a
  different meaning, and no calibration is measured at this level.
- Correct absence counts as correct: D04 due_date is absent in
  the document, so extracting None is right, and it still goes
  to the review queue so a human confirms the absence.
- No table extraction, no question answering across documents,
  and no review workflow beyond the queue list. Those are Build
  and Deep scope.
- This level was run on the Muse VM (CPU), not on its assigned
  fleet node, the Dell R610.

## Build stage (moved from level-2-build/README.md)

Status: DONE (2026-11-05). An end-to-end pipeline over 32
synthetic plain-text documents: field extraction reusing the
Learn extractor by import plus Build receipt patterns,
line-item table extraction, per-document records, and a
cross-document QA layer answering aggregate and lookup
questions from extracted records only, each answer citing the
document ids it used. An eval harness scores fields, table
rows and cells, and QA answers. Python standard library only.

### Honest scope line

There is NO OCR and NO LLM in this level, and both are named
substitutions (see PROPOSAL.md (Build plan), written before the code).
No OCR engine is available on the Muse VM (`which tesseract`
returns nothing, checked 2026-11-05) and no LLM is available
either. The pipeline ingests synthetic plain-text documents
in the layout an OCR step would produce, and extraction is
rule-based (the Learn extractor plus receipt patterns), not
an LLM. No claim is made about images, scans, PDFs, or LLM
extraction. The assigned Dell R610 was unreachable for this
cycle, no live capture is claimed, and the run was on the
Muse VM: that is named as a limit below.

### Method

1. Corpus (corpus.py). 32 synthetic documents: 16 invoices,
   8 purchase forms, 8 receipts, in 2 layout variants per
   type (6 variants). Variant A uses pipe-separated tables
   and primary labels; variant B uses semicolon tables and
   alternate labels; receipts add Store, Receipt Number,
   Receipt No, and Paid labels. Every document carries a
   line-item table and ground truth for the 5 Learn fields
   plus its table rows. Authored arithmetic is exact: each
   line total is quantity times unit price, and each document
   total is the sum of its line totals (a test checks this
   for all 32 documents and all 65 rows).
2. Known hard cases. B15 renders its date in words and B16
   renders its total in words. The extractor is expected to
   miss both fields, as in Learn document D08. Receipts have
   no due date: ground truth is None, and a correctly
   detected absence counts as correct, as in Learn.
3. Table format (stated). A header row naming item, qty,
   unit price, and line total, separated by pipe or
   semicolon; each following row with the same delimiter and
   exactly 4 cells (item, integer quantity, dollar unit
   price, dollar line total) is a line item; the table ends
   at the first line without that delimiter.
4. Field extraction (pipeline.py). The Learn extractor is
   imported and reused. Build patterns for the receipt
   labels run first for invoice_number, vendor, and total,
   because the Learn vendor fallback would otherwise take
   the RECEIPT header line as a vendor. Confidence uses the
   Learn rule (1.00 primary, 0.80 alternate, 0.60 fallback,
   0.00 missing), with receipt primary labels at 1.00 and
   Paid at 0.80.
5. Records and QA (pipeline.py, qa.py). Each document
   becomes one record: extracted fields, confidences, and
   line items. Records carry no ground truth (a test checks
   this), so the QA layer can only answer from extracted
   values. Questions are structured dicts (type plus
   params), not natural language, because no LLM is
   available. Nine question types cover total spend per
   vendor, total spend overall and per kind, the largest
   document, counts by vendor and by kind, line items for a
   named invoice, the vendor of a named invoice, and
   documents over an amount. A record with a missed total
   contributes nothing to a spend sum and is not cited for
   it, so a missed field changes the answer visibly.
6. Eval harness (eval_build.py). Per-field accuracy over
   32 x 5 fields; table row accuracy (rows exactly correct,
   all 4 cells in authored order, over total rows) and cell
   accuracy (over rows x 4, a missing row scores 0 for its
   cells, extra rows counted separately); QA accuracy over
   16 labelled questions, where an answer counts as correct
   only when its value and its cited document ids both equal
   the gold. Gold QA answers are computed by independent
   aggregation code in eval_build.py over ground truth, and
   the tests add hand-computed expectations.

## Deep stage (moved from level-3-deep/README.md)

Status: DONE (2026-11-05). Per-field confidence calibration
against the Build eval, with the review queue measured.
The Build pipeline runs over its own 32-document eval,
unchanged, and every one of the 160 extracted fields is
scored against ground truth and bucketed by its stated
confidence value. Calibration error is computed by a stated
formula, and a threshold sweep measures what the review
queue captures and what it costs. Python standard library
only. Compressed Deep under the December Compression
Protocol: this is the single hardest capability in the
SPEC Deep scope; the rest of the v2 Deep scope is the
named v1.1 backlog in the Next cycle section of PROPOSAL.md.

### Honest scope line

There is NO OCR and NO LLM in this level, and both remain
named substitutions from Build (see PROPOSAL.md (Deep plan), written
before the code). No OCR engine is available on this VM
(`which tesseract` returns nothing, checked 2026-11-05 at
Build) and no LLM is available either. The input is
synthetic plain text in the layout an OCR step would
produce, and extraction is rule-based. Deep calibrates the
rule-based confidence scores only: no claim is made about
images, scans, PDFs, or LLM extraction, and no OCR or LLM
result is reported anywhere in this level. The assigned
Dell R610 was not used: the run was on the Muse VM, and
that is named as a limit below. The eval set is NOT
extended: extending the Build corpus would change every
Build number, so Deep measures the same 32 documents and
160 fields, and the small error count that follows (2
errors) is named as a limit below, not hidden.

### Method

1. Items (calibration.py). One item per extracted field:
   document id, field, stated confidence, extracted value,
   ground truth, correct flag (exact match; a correctly
   detected absence counts as correct, as in Learn and
   Build), and a missing flag.
2. Bands. The confidence rule uses exactly four stated
   values, so the bands are those values: 0.00, 0.60, 0.80,
   and 1.00. No binning choice is hidden. Per band: count,
   correct count, accuracy, and the absolute gap between
   accuracy and the band confidence value. Per field:
   overall accuracy and accuracy inside each band the
   field uses.
3. Calibration error. Expected calibration error over the
   bands, formula stated in PROPOSAL.md (Deep plan):

       ECE = sum over bands b of (n_b / N) * |acc_b - conf_b|

   with N = 160. The Brier score over the same items is a
   secondary measure: mean of (confidence - outcome)^2,
   outcome 1 when correct, 0 when wrong.
4. Review queue, measured. A sweep over three candidate
   flag rules: confidence below 0.60, below 0.80 (the
   Learn queue rule), and below 1.00. For each rule: fields
   flagged, review burden (fields flagged / 160),
   documents flagged (any flagged field), errors captured,
   error capture rate (errors captured / 2 total errors),
   and flagged-but-correct count. The recommended
   threshold is the lowest-burden rule that captures every
   error.
5. All arithmetic is computed by calibration.py and
   written to results_deep.json. Every number in this
   README is read from that file, and the unit tests carry
   hand-computed expectations for the band table, the ECE,
   the Brier score, and the queue.

### Verdict: are the confidence scores trustworthy?

No, not as probabilities, and the tables show why in
three separate ways.

1. Every non-zero band is underconfident. Fields scored
   0.60 are right 4 of 4 times, fields scored 0.80 are
   right 47 of 47 times, and fields scored 1.00 are right
   99 of 99 times. Read as probabilities, 0.60 and 0.80
   both understate the measured accuracy by a wide
   margin, and the ECE of 0.1187 is entirely this
   underconfidence: the gap between 0.9875 accuracy and
   0.8688 mean confidence.
2. The 0.00 band pools two opposite meanings. At field
   level, confidence 0.00 on due_date is 8 of 8 correct
   (receipts genuinely have no due date), while
   confidence 0.00 on date and total is 0 of 2 correct
   (real values the extractor missed). The pooled band
   accuracy of 0.8000 describes neither case. The value
   0.00 means "nothing matched", and whether that is an
   error depends on whether the field should exist, which
   the score itself does not say.
3. The scores are still useful as a ranking. Both errors
   sit at the lowest value, no error sits at 0.60 or
   above, and accuracy is monotone in the score on this
   eval. As route labels that sort fields for review,
   they work. As probabilities of correctness, they do
   not.

Threshold the evidence supports: flag confidence below
0.60. It captures both errors (capture rate 1.0000) at
the lowest burden in the sweep, 10 of 160 fields
(0.0625) across 10 of 32 documents. The Learn rule
(below 0.80) adds 4 reviews and captures no extra error,
and flagging below 1.00 adds 51 more reviews and still
captures no extra error. The honest limit on this
recommendation: it rests on 2 errors total. With so few
errors, the sweep cannot show that a 0.60 or 0.80 field
is never wrong; it only shows none was wrong here. The
threshold is the best supported by this eval, not a
proven safe line, and it should be re-measured on a
larger eval before it is trusted in production.

### Failure modes and limits

- Synthetic documents only: the same 32 authored
  documents as Build, with invented vendors. Real
  documents add layout noise and wording variety that
  could move errors into higher confidence bands, which
  this eval cannot see.
- No OCR and no LLM: the SPEC headline capabilities
  remain named substitutions (plain-text input in OCR
  layout, rule-based extraction). Calibration of a real
  OCR engine score or an LLM self-reported confidence is
  a different measurement and is not claimed.
- Only 2 errors: every capture rate and every low-band
  accuracy rests on tiny counts. The 0.60 band has 4
  fields and the error set has 2 items, so a capture rate
  of 1.0000 is a statement about this eval, not a bound
  on future errors.
- Four discrete route values, not a probability model:
  the calibration measures the Learn route rule (1.00
  primary, 0.80 alternate, 0.60 fallback, 0.00 missing).
  There is no learned scorer to recalibrate here; a
  recalibration map fitted on 160 fields with 2 errors
  would be curve fitting to noise, so none is fitted.
- The 0.00 band confound: pooled band accuracy mixes
  correct absences with real misses. Any consumer of the
  band table alone, without the per-field split, would
  misread the lowest band in both directions.
- Correct absence counts as correct: this follows Learn
  and Build, and it is what makes receipt due_date score
  1.0000 at confidence 0.00. Under a convention where an
  absence is not scored, the 0.00 band would read 0 of 2
  and the ECE would change. The convention is stated,
  not hidden.
- The queue is measured offline only: no human review
  workflow, review time, or reviewer accuracy is
  measured. Burden is counted in fields and documents,
  not minutes.
- Threshold fitted and tested on the same eval: the
  recommended threshold is chosen from the sweep over
  the same 160 fields it is then reported on. There is
  no held-out set, so the recommendation carries
  selection bias, named here rather than hidden.
- Run on the Muse VM, not the assigned Dell R610 fleet
  node.

### 1. Research question

Question as built: on a synthetic document corpus, how accurate are
hand-written extraction rules per field, and are their stated confidence
values calibrated probabilities?

Gap found: the README tagline and SPEC described the project as OCR
plus model-based extraction, which the shipped code does not do. Fixed: README
and SPEC now state the target scope and the shipped scope side by side
("rule-based over synthetic text, no OCR, no language model").

### 2. Hypotheses

The Deep level tests one hypothesis with a written verdict: the stated
confidence values behave as probabilities of correctness. Rejected:
every non-zero band is underconfident and the 0.00 band mixes two
meanings. The Learn and Build levels have acceptance criteria rather
than falsifiable hypotheses. Remaining gap: no pre-registered hypothesis
with a falsification threshold. Needs no compute, only a written
pre-registration before the next eval set is built (Next cycle item 1).

### 3. Method

Strong. PROPOSAL.md (Build plan) and PROPOSAL.md (Deep plan) were written before the code;
ECE and Brier formulas are stated; bands are the four stated values, so
no binning choice is hidden; gold QA answers are derived independently
of the QA code. Added: a JavaScript port of the extractor, QA and
calibration code whose parity with the Python results is asserted on
every site build (site/src/parity.check.mjs). That doubles as a
cross-implementation test of the extractor.

### 4. Baselines

Gap found: no baseline for calibration. Fixed (src/calibration.py,
key `baselines` in results_deep.json):

- Constant confidence equal to the overall accuracy: ECE 0.0000, Brier
  0.0123.
- In-sample band-accuracy map: ECE 0.0000, Brier 0.0100.
- Stated route labels: ECE 0.1187, Brier 0.0658.

Both baselines are fitted on the items they are scored on and are
labelled in-sample. They show that most of the Brier score is the
labels' values, not ranking failure. Remaining gap: an out-of-sample
recalibration baseline. Needs a held-out eval of a few hundred labelled
fields with enough errors to fit on (Next cycle items 1, 5 and 6); CPU
only, minutes to run, but the data does not exist yet.

There is no extraction baseline beyond the rules (for example an OCR
engine or a learned extractor). Needs an OCR engine and a free or local
model on the same corpus (Next cycle items 3 and 4).

### 5. Statistics and uncertainty

Gap found: no interval estimate anywhere, while capture rate and band
accuracies rest on 2 errors. Fixed: Wilson 95% intervals (stdlib math,
`wilson_interval` in calibration.py, unit-tested by hand) on every band
accuracy, every per-field accuracy, every group in the new cuts, and the
error capture rate. Capture of 2 of 2 has an interval of 0.3424 to 1.0.
The dashboard draws these as whiskers, computed in the browser and
checked against the Python values at build time.

Added per-kind, per-variant and per-layout cuts (key `breakdowns`),
labelled indicative only because each group holds 0 to 2 errors.

Remaining gap: power. With 2 errors, no capture rate or band accuracy
can be estimated tightly. Needs a larger labelled eval (Next cycle item 1):
roughly 30 or more errors would bring a Wilson interval on capture rate
to about plus or minus 0.15.

### 6. Reproducibility

Strong. Standard library only; all three runners and the new stress
runner are deterministic, and the committed results files are checked
by `git diff --exit-code` after a rerun. CI runs on Python 3.11 and
3.12. New: unit tests assert that results/results_stress.json and
results/documents_export.json match a fresh run, and the site
build fails if the browser port drifts from any committed result.

### 7. Threats to validity

Named in every level README. Added one measurement: a deterministic
perturbation stress set (src/stress.py, results/results_stress.json),
reported separately from the main eval. Four fixed format shifts on all
32 documents with labels unchanged:

| Shift | Fields correct | Table rows |
| --- | --- | --- |
| Labels lower-cased | 47 / 160 | 65 / 65 |
| Lines indented two spaces | 43 / 160 | 65 / 65 |
| Dates as DD/MM/YYYY | 103 / 160 | 65 / 65 |
| Dollar sign removed | 127 / 160 | 0 / 65 |

The rules are format-bound: the 0.9875 headline holds only for the
exact formats the rules were written for. Remaining threats:

- Same author wrote corpus, rules and shifts. Needs an independently
  authored or real document set (Next cycle items 1 and 2).
- Threshold chosen on the same eval it is scored on. Needs a held-out
  split of a larger eval (Next cycle item 5).
- Run location: the Muse VM, not the assigned Dell R610. Needs one run
  on the R610 (Next cycle item 10); seconds of CPU.

### 8. Related work

Gap found: DOSSIER.md Past (now PROPOSAL.md, Prior work) has no dated
citations and NOVELTY.md was a placeholder. Partly fixed: NOVELTY.md (now
